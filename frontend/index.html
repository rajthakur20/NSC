💡 How It Works

Comprehensive educational guide to the cryptographic primitives powering this application.

SECTION 1

AES-256-GCM (Advanced Encryption Standard - Galois/Counter Mode)

AES encrypts the file so unauthorized people cannot read it. GCM also provides authentication so modifications can be detected.

Standard symmetric ciphers (like AES in CBC or ECB mode) only provide confidentiality — they do not protect against bit-flipping or tampering. AES-GCM is an Authenticated Encryption with Associated Data (AEAD) cipher. It combines counter-mode encryption with a universal Galois hash (GHASH) to produce a 128-bit authentication tag.

Plaintext Bytes + AAD (Container Header) + Nonce (96-bit) + 256-bit Key ↓ AES-GCM Engine ↓ Ciphertext + 128-bit Authentication Tag (Tamper-Proof)
SECTION 2

SHA-256 (Secure Hash Algorithm 256-bit)

A file is converted into a unique-looking fixed-length hash. Even a small file modification normally produces a completely different hash.

SHA-256 maps arbitrary-length input into a 256-bit (64 hexadecimal characters) output digest. It exhibits the Avalanche Effect: changing even a single bit in a 10 GB file will flip approximately 50% of the output bits, making deliberate modifications or accidental corruption immediately visible.

SECTION 3

PBKDF2 (Password-Based Key Derivation Function 2)

PBKDF2 converts a human password into a cryptographic key using a salt and repeated hashing.

Humans choose memorable passphrases with low entropy. Directly hashing a password does not yield a secure 256-bit key. PBKDF2-HMAC-SHA256 applies a pseudo-random function over 100,000 iterations along with a salt. This deliberate computational cost slows down offline dictionary and GPU brute-force attacks by several orders of magnitude.

SECTION 4

Cryptographic Salt

A random salt makes password-derived keys different even when the same password is used.

A 16-byte random salt generated via CSPRNG (Cryptographically Secure Pseudo-Random Number Generator) is prepended before key derivation. This ensures two users with identical passwords will generate completely distinct AES keys, defeating precomputed Rainbow Table attacks. The salt is stored openly in the container header because salts are not secret.

SECTION 5

Nonce (Number Used Once)

AES-GCM requires a fresh nonce for each encryption operation.

In Galois/Counter Mode, nonces must never be repeated with the same key. Nonce reuse with AES-GCM can catastrophically leak the authentication key and plaintext XOR streams. This tool generates a fresh, random 96-bit (12-byte) nonce for every single encryption request.

Viva Quick Guide

When presenting this project to your examiner:

  • Why AES-GCM instead of AES-CBC? GCM provides AEAD (Authenticated Encryption with Associated Data). It guarantees both privacy AND integrity, eliminating padding oracle vulnerabilities.
  • Why PBKDF2? Prevents brute force and dictionary attacks by stretching low-entropy passwords using a random salt and 100,000 rounds of HMAC-SHA256.
  • Where are passwords stored? Nowhere. The application is completely zero-knowledge and database-free.
  • How is tampering detected? If a single bit in the ciphertext or header changes, the GCM Galois hash tag calculation fails and throws an authentication error.
